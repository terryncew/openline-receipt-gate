# Owner review packet — one Lithic sandbox card, $1 per attempt

**Current decision: accept the offline preflight; defer the external approval/revocation/successor run.** Its two gates are a reproducible real-provider intent template and actual-program failure/default behavior. The next useful work is provider-specific evidence and, if needed, a separately approved unarmed calibration. This packet authorizes nothing and requests no action now.

## Proposed purpose and bounds

Demonstrate portable owner delegation enforced by a receiver operated independently of the worker: A approves; an admitted owner-signed revocation disables an already pending A intent across restart; B receives new authority and approves on the same card. Independently pinned receipt signatures and provider transaction records must agree.

The owner grants reusable `lithic:authorize` scope. The receiver restricts each authorized purchase to exactly 100 USD cents, and the worker signs its terms. This is **not** owner-signed exact purchase consent, an aggregate $1 cap, or exact merchant-order binding. A pending intent lasts at most 60 seconds and is consumed by the first matching authenticated callback. Use one exclusively controlled card with no earlier in-flight matching request or competing use.

The minimum full sequence requires **three distinct $1 authorization attempts, two intended approvals ($2 total synthetic authorized), one intended decline, zero clearing or settlement requests**. One total authorization attempt cannot demonstrate all three stages. Optional template calibration adds **one separately approved $1 attempt expected to decline**. Any provider-failure trial, issuance, rotation or extra attempt needs separate scope. Disable automatic simulator retries; an ambiguous outcome never permits another simulator call.

## Before an external attempt

1. **Named sandbox resources and costs.** Owner identifies the authorized operator, sandbox program, one OPEN VIRTUAL card, receiver host/operator and integrator. Verify sandbox API base URL and credential scope. Confirm ASA access, fees/restrictions/rate limits and available authorization capacity; no cost is assumed to be zero. Use existing approved hosting where possible. Any hosting/domain/TLS cost, new service or provider fee requires an explicit ceiling/permission; none is approved here.

2. **Provider safety and template gates.** Record applicable program behavior for receiver connection failure, timeout, malformed response and exhausted callback retries, plus its response deadline. The provider must not approve through a default policy when this receiver cannot authorize. Existing authoritative program evidence may resolve this; do not invent a `fail_open` enrollment option or require a new research project. Resolve actual predictable callback terms through a guaranteed program template or the separately approved calibration below. Unstable bound metadata means stop and review the smallest necessary intent-contract change before implementation.

3. **Credentials kept separate.** The control-plane operator alone holds the sandbox API key and simulator PAN access. Workers A/B hold only their own signing keys and authorized protocol inputs; they do not receive API/ASA/receiver/integrator credentials or receiver administration. Receiver holds the actual program ASA signing secret and its own receipt key/state. Integrator receives a separately provisioned strong random receipt bearer credential (at least 32 characters), locally enrolled to this owner; the receiver stores only its hash. The ASA secret is neither the API key nor an ordinary webhook subscription secret. Inject values securely, never through chat, PRs or logs. Actual key material is necessary for local HMAC; a proxy placeholder is insufficient.

4. **Owner and receiver enrollment.** Authenticate the real owner's relationship to the card account. Pin the owner's root public key through an independent trusted channel, not merely a bundle's embedded key. Owner retains its root private key. Initialize the receiver key once on the approved protected host; authenticate its public key/fingerprint to the integrator **before** any ASA response. Keep gate ID and receiver pin stable across restart; reopen with the expected pin. Laboratory public keys are examples, not real pilot enrollment.

5. **Safe endpoint.** Run the exact delivered runtime (`8a537d4ff598541bb21cc564b3220ec97ef09fb3`, runtime identical to tested `abf6bc72f4375bd43d2c274812e5dadd68f03e41`) as a supervised process bound to loopback behind approved trusted-certificate HTTPS ingress. Preserve raw body bytes and the three signature headers, reject ambiguous duplicates/framing, do not parse/reserialize before verification, and forward finite Content-Length because this receiver refuses Transfer-Encoding. Keep administration local. Protect SQLite/WAL/SHM and credentials, retain persistent state across restart, use a stable clock, and prohibit restoration of old state. Disable raw-body/header/credential logging and caching. Receipt route must remain authenticated and read-only.

6. **Enrollment and signing activation.** Inspect the authorized program's existing responder configuration before a reviewed `POST /v1/responder_endpoints` with `{"type":"AUTH_STREAM_ACCESS","url":"https://<approved-host>/asa"}`; do not overwrite an unrelated endpoint. `GET /v1/auth_stream/secret` may create a secret and activate signature headers, so its use needs explicit permission despite GET. Confirm actual deliveries have valid signature headers before arming authority. Secret rotation is outside this run; if separately authorized, account for the documented 24-hour old-secret overlap.

7. **Bounded caller and independent safety controls.** Use an explicitly sandbox-only SDK client with `max_retries=0` and a finite timeout. Record each simulator POST once; never retry after an ambiguous error until authorized provider records resolve it. Keep card state, provider limits/rules and sufficient remaining allowance unchanged across the three stages. A 100-cent TRANSACTION limit is per request, not aggregate; an exhausted 100-cent FOREVER limit would mask revocation and prevent successor success. Do not use a provider cap/pause as evidence that OpenLine rejected revoked authority.

## Nonsecret simulator parameters and calibration

Proposed `/v1/simulate/authorize` parameters: `amount=100`, `descriptor="OPENLINE PILOT"`, `merchant_acceptor_id="OL-PILOT-001"` (within the 15-character maximum), city/state/country `NEW YORK`/`NY`/`USA`, `mcc="5999"`, `merchant_amount=100`, `merchant_currency="USD"`, `status="AUTHORIZATION"`, `partial_approval_capable=false`. Supply the selected sandbox PAN only through the secure runtime binding. Omit PIN. The fixture's 22-character ID cannot be replayed as simulator input. Do not use FINANCIAL_AUTHORIZATION, advice, clearing, settlement, credit, reversal or production endpoints.

With a reviewed current SDK exposing it, also set `billing_currency="USD"`; pinned 0.132.0 does not accept that newer argument, so confirm the program's USD billing rather than pass an unsupported parameter. Explicit merchant currency is required: its default with merchant amount supplied is GBP.

These arguments do not set all intent-bound provider fields. If a guaranteed template is unavailable and the safety gate is satisfied, separately approve **one unarmed calibration**: card binding only, no pending intent, one simulator POST. Require valid real-provider HMAC, local HTTP 200 `{"result":"CARD_PAUSED"}`, and provider decline. Privately capture the exact authenticated callback and normalize it for the next signed intent. Check acquiring institution, amounts, initiator, network/POS/AVS/risk/authentication and other bound context for predictability; do not guess them from laboratory JSON. A sample alone does not guarantee future stability. Any drift in later requests stops the run safely and must be reviewed.

## The three-stage acceptance run

| Stage | Action and expected observable results |
| --- | --- |
| **A approval** | Owner grants A genuine Wallet authority; receiver admits the verified bundle and locally binds the same card to A. A uses a fresh receiver challenge, real Wallet presentation and signed confirmed terms; preauthorization succeeds. Exactly one $1 simulator request within the intent window produces a valid ASA, HTTP 200 APPROVED, one consumed pending intent and one durable receipt naming A. Verify provider AUTHORIZATION event/result agrees. Restart with original receiver pin and confirm persisted receipt retrieval. |
| **Owner revocation → decline** | Before revoking, create a fresh, otherwise-valid, **unconsumed A intent** and record its expiry. Owner signs revoke and exports a newer bundle; receiver admission must commit and remove pending authority. Record old/new heads and completed admission time. Restart with retained state, then send exactly one new matching $1 transaction while the removed intent would otherwise still be valid. Require HTTP 200 CARD_PAUSED, a signed decline, and provider decline while issuer controls and allowance remain unchanged. An expired intent or exhausted card cap makes the causal test inconclusive. Normal receipt reason is NO_PENDING_AUTHORIZATION; signed revocation plus admission ordering supplies causal evidence. |
| **B successor approval** | Owner grants B a new mandate/key; admit its new bundle and bind the **same card** to B. Fresh B challenge/presentation/intent succeeds; restart/reopen retained state if within expiry, then one new $1 transaction returns HTTP 200 APPROVED and a receipt naming B/new mandate, with provider approval. A cannot reuse B authority. Verify all persisted receipts after restart. |

Make one new simulation attempt at each stage; record Lithic's returned transaction-group token and verify it differs from earlier stages. The caller cannot preselect that token. An identical provider retry of A's already committed token correctly returns its historical APPROVED decision even after revocation; it is not the revocation test. Do not create a new simulator transaction to imitate a retry. Local stale-bundle, old-worker, mismatch, replay and tampering checks are already passing and need not add external attempts.

For each external attempt record the SDK version/base URL/retry setting, simulator response `token` and debugging request ID, authenticated callback fingerprint/token/terms, receipt, complete response timing, committed authority head/admission ordering, and redacted provider card/rule/remaining-allowance snapshot. A simulator HTTP 201 contains a token, **not proof of approval**. Read the corresponding provider transaction authorization event/result and compare it with the receiver decision; do not rely on a nonexistent generic `asa_responded` field.

Retrieve `GET /receipts/{transaction-token}` over the approved HTTPS/private route using the owner's integrator bearer. Independently reconstruct the canonical receipt payload, check its SHA-256 and Ed25519 signature against the previously authenticated receiver pin, and compare result/token/fingerprint/card/amount/currency/worker/mandate. Separately verify root-signed bundles and epoch certificates against the prior owner pin, grants/successor grants against their root-certified epoch key, root-signed revocation against the owner pin, and history ancestry. An embedded receipt key, a valid signature alone, or three result strings alone is insufficient evidence of the enforcement sequence.

## Failure and immediate stop

Stop before arming if either provider gate, owner/card enrollment, pin provenance, credentials, cost ceiling or host protection is unresolved. During execution stop on invalid/missing HMAC, field/template drift, wrong amount/currency/card/operation, wrong pin, corrupt/unavailable/restored state, unexpected retry/extra token, missing or invalid receipt, ambiguous timeout, disagreement between provider and receiver, revoked/unarmed approval, or response exceeding the actual provider deadline or local six-second budget. Unexpected external costs, production resources or secret disclosure also stop immediately.

Issue no further simulation calls after ambiguity. Preserve private evidence and investigate via already authorized read-only records. The future approval should name an emergency operator and separately authorize safe disarming/card pause/endpoint cleanup if needed; revocation alone cannot compensate for an unknown provider fallback, and endpoint removal may change fallback behavior. Do not perform those external control-plane actions under this audit.

A successful run proves a receiver authorization decision and provider handling in this sandbox. It does not prove goods, settlement, hostile-host protection, rollback-safe recovery, instantaneous undelivered revocation, production availability or superiority over an equivalent stateful policy gate. **Owner review ends this task; no external action is approved.**
