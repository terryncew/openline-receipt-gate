# Independent receiver authority audit

Review target: `terryncew/openline-receipt-gate` PR #108, clean HEAD `8a537d4ff598541bb21cc564b3220ec97ef09fb3`. Adapter, vendored Wallet and selected regressions have no diff from tested implementation `abf6bc72f4375bd43d2c274812e5dadd68f03e41`. No repository files, external accounts, cards, transactions or services were changed.

## Finding and verdict

I found no cryptographic or admission-ordering blocker for the explicitly bounded pilot: one controlled card, $1 per purchase authorization, trusted independently operated receiver, fresh worker intents, no competing matching traffic, successful delivery/admission of revocation updates, and no restoration of old receiver state.

Owner acceptance must describe delegated scope and first matching ASA arrival accurately. The owner does not sign exact payment terms, the grant is reusable, and a matching purchase initiated before an intent can consume that intent on later delivery. These are material consent and operational conditions. They become blockers if the proposed acceptance promises one total $1 spend, exact owner-approved merchant/order/transaction, or only purchases initiated after owner authorization.

## Independent evidence

- `verify_public_chain.py` imports cryptography, not the adapter or Wallet verifier. It verified 19 Ed25519 signatures including repeated history: three root-signed bundles, three root-certified epoch certificates, six signed historical events, three receiver receipts and four embedded receiver-decision/worker-intent signatures. Bundle ancestry is exactly heads 1 → 2 → 3; event sequence is certified-epoch grant → owner-root revocation → certified-epoch successor grant. Receipt sequence is APPROVED → CARD_PAUSED → APPROVED. The receiver key came from the separate `receiver-pinned.pub`, not an adopted receipt key.
- The public evidence alone does not prove external key-pin provenance, the actual worker presentation bytes or receiver-issued challenges, authenticated ASA bodies, pending-row invalidation, restarts, or commit atomicity. Those are supported by executable code and tests, not merely the signed public JSON.
- Fresh run of the existing real-Wallet authority suite: 21 tests passed, including both revocation/ASA orderings, cross-adapter visibility, stale-head prevention, signed-fork quarantine and restart. Tests were copied into scratch and run with Python 3.12.14 / cryptography 50.0.1 and the reviewed source on PYTHONPATH.
- Six custom probes passed. Their observations are retained in `authority-probe-result.json` and source in `probe_authority_limits.py`.

## Minimal owner-facing corrections

Describe the accepted object as a reusable delegation allowing the worker to create one pending $1 intent at a time. Say the first matching authenticated ASA delivery can consume it, including a delayed earlier unseen request; neither an exact merchant order nor a total spending cap is authenticated by the owner's grant. Require the controlled-card/no-in-flight-matching-traffic conditions before any externally connected sandbox test. These corrections make the consent concrete without inventing production requirements.

The existing documents already disclose worker-signed terms, identical-detail ambiguity, admission-based revocation, trusted-host storage and unsupported rollback. No claim should turn these scoped guarantees into exact-purchase owner approval or instantaneous revocation.
