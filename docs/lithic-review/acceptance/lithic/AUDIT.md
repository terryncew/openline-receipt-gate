# Independent Lithic acceptance audit

Audit date: 2026-10-11 UTC. Delivery HEAD: `8a537d4ff598541bb21cc564b3220ec97ef09fb3`. Tested implementation claimed by existing report: `abf6bc72f4375bd43d2c274812e5dadd68f03e41`. This read-only audit independently assessed the current sources and reran the HMAC conformance tests. It did not assume the earlier READY claim established external acceptance.

## Conclusion

The ASA schema, minimal response values, and implemented signing algorithm are supported by official pinned evidence. External Lithic interoperability remains untested and has specific prerequisites. The supplied fixture is not directly reproducible by the official sandbox simulator, and simulator parameters alone do not establish all fields needed to construct an exact matching worker-signed intent. This blocks a claim that the current artifacts already constitute an executable real-provider acceptance run. It is not proof that an actual delivered simulator request would always fail.

## Findings

1. **External acceptance blocker — exact intent preparation is unestablished.** `openline_receiver/lithic_adapter.py:101–108` binds the complete `amounts` and `merchant` objects plus supplied network, POS, authentication, AVS, service-location, risk, fleet, and challenge context. `:512–513` requires those normalized details to equal the signed pending intent. The official simulator parameters do not expose `merchant.acquiring_institution_id`, `transaction_initiator`, POS, AVS, risk/authentication fields, fee/cash fields, or hold/settlement objects. An arbitrary fixture cannot certify their actual values. Smallest safe step: after explicit external authorization and fail-closed fallback confirmation, obtain a provider-signed sample with no pending intent, establish which fields are stable for the chosen sandbox scenario, and prepare the next matching intent from a confirmed provider template. If provider-generated bound fields vary per request, stop and separately design a narrower owner-approved intent contract; do not silently remove signed constraints.

2. **Concrete external packet mismatch — fixture merchant ID cannot be sent to simulator.** Fixture `merchant.acceptor_id` is `OPENLINE-SYNTHETIC-001` (22 characters). Pinned OpenAPI `/v1/simulate/authorize` sets `merchant_acceptor_id.maxLength = 15`. Independent JSON Schema validation rejects that field when used as a simulator input. Use a new permitted value such as `OL-PILOT-001` and obtain/sign confirmed matching details. The fixture remains a valid ASA payload because the ASA merchant schema does not impose this simulator limit.

3. **External prerequisite — provider fallback is unverified.** Actual ASA enrollment is `POST /v1/responder_endpoints` with `type: AUTH_STREAM_ACCESS` and `url`. No `fail_open` or default-policy field appears in the pinned enrollment schema. The GET status response only exposes `enrolled` and `url`. Neither local adapter declines nor a fabricated `fail_open:false` enrollment parameter proves that Lithic declines on timeout/malformed response/exhausted retry. Retain program-specific evidence of that behavior before enabling an external endpoint or spending intent. No need to contact anyone within this audit.

4. **Timing boundary — only a requested local six-second budget is established.** Pinned official ASA webhook schema supports handled HTTP 200 and an immediate single retry after HTTP 5XX. It does not specify the provider's total deadline, timeout-retry behavior, or delivery guarantee. The repository correctly describes six seconds as local measurements. The HTTP server is loopback-only and supplies no public TLS hosting, so measured localhost timings do not establish the complete provider round trip. Confirm the provider deadline and measure the deployed ingress-to-complete-response path under the authorized sandbox run.

5. **Secret lifecycle must be explicit.** ASA uses the program secret, not the API key or an ordinary webhook subscription secret. `GET /v1/auth_stream/secret` creates the key if missing and enables signature headers shortly afterward, so it is write-affecting despite GET. Rotation `POST /v1/auth_stream/secret/rotate` returns no key; retrieve the new key via GET, keep only the explicit current/previous keys for the documented overlap, and remove the retired key by its 24-hour deactivation. A proxy placeholder is not usable as a local HMAC key; the verifier needs securely injected actual key material.

6. **Bounded-run prerequisite — disable simulator client retries.** SDK v0.132.0 defaults to `max_retries=2` and has no automatic idempotency header configured. A providerless `httpx.MockTransport` check returned a mocked HTTP 500: the default client made three `POST /v1/simulate/authorize` attempts; `max_retries=0` made one. This is distinct from Lithic retrying one ASA request after receiver HTTP 5XX. Use an explicitly sandbox-only simulator client with `max_retries=0`, and stop after ambiguous timeout rather than create another transaction to retry a delivery. `sdk-simulation-retries.json` records the mock result.

- `PYTHONDONTWRITEBYTECODE=1 OPENLINE_REQUIRE_OFFICIAL_LITHIC=1 /workspace/lithic-hmac-sdk-venv/bin/python -m unittest -v test_lithic_hmac` completed: 12 tests, all passed, no skips. - Actual documented headers are `webhook-id`, integer Unix `webhook-timestamp`, and a space-separated `webhook-signature` list of versioned Base64 HMAC values. The HTTP handler rejects duplicate auth headers and verifies unchanged raw bytes before JSON.
- Current pinned Python SDK simulation input at commit `826a8c940571e88bd4682a38e22b1c9f999cef93` additionally exposes `billing_currency` and `settlement_currency`. Its `merchant_currency` defaults to GBP if `merchant_amount` is supplied; set merchant amount 100 and currency USD explicitly. Current billing currency defaults USD but should also be explicit when using that SDK. This does not resolve the undisclosed generated intent fields.
- A simulation HTTP 201 response contains transaction token and debugging request ID, not an ASA approval result. Provider transaction retrieval and the receiver's signed receipt must be checked separately.
- No exported environment-variable names matching LITHIC, ASA, INTEGRATOR, or RECEIVER were present. No values or credential files were inspected. This is a narrow name-presence observation, not proof that all platform secret bindings are absent.

## Limits and artifacts

HTTPS with a trusted certificate remains necessary for the proposed secure pilot's credential/body transport.
